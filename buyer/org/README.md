# buyer/org

The warm tier: a Privy organization wallet, the humans who operate it, and the
two key quorums that decide what one of them can do alone.

Full writeup, with the live transcript and every verified id: `docs/privy-mandate.md`.

```bash
npm run privy:setup              # operators, quorums, mandate policy, org wallet
npm run privy:setup -- --status  # read it back
npm run privy:mandate            # the refusal, and the quorum that answers it
```

## The shape

| File | What it is |
|---|---|
| `authorization-key.ts` | P-256 keys, RFC 8785 canonicalization, the ECDSA signature |
| `privy.ts` | The REST client |
| `operators.ts` | Humans as Privy users with embedded wallets; `createKeyQuorum` |
| `org-wallet.ts` | The server wallet, and `eth_signTransaction` |
| `fund-agent.ts` | `approve` + `depositFor`, signed at Privy, broadcast by us |
| `env.ts` | Reassembling the org from `.env` |

## Two quorums, and why it is two and not one

| Quorum | Threshold | Owns | So this needs |
|---|---|---|---|
| **operations** | 1 of N | the org wallet | any one operator, for a routine treasury op |
| **board** | 2 of N | the mandate policy | two operators, to widen what the agent may spend |

One quorum cannot express that. A 2-of-N wallet means funding the agent needs a
meeting; a 1-of-N policy means one compromised operator key can raise the cap and
then spend against it — which is the failure `CLAUDE.md` exists to prevent:

> **the key that spends can never raise its own limit.**

The ordinary operation takes one signature and the *change to the rules* takes
two. That asymmetry is the whole control.

## Two authentications, stacked

They are not alternatives:

1. **HTTP basic auth** with `app_id:app_secret` proves *which app* is calling.
   Every request carries it.
2. **`privy-authorization-signature`**, one per approving operator, proves *who
   authorized this specific request*. Only mutations of an owned resource carry
   it, and the signature covers the URL, the body and the `privy-` headers, so it
   cannot be replayed against a different request.

**The app secret alone cannot raise the mandate cap.** Our server can be fully
compromised and the cap still holds, because Privy's enclave wants signatures
from keys the server never held.

## Why a hand-rolled client rather than Privy's SDK

The interesting part of this integration is the authorization signature, and an
SDK that computes it for you is an SDK that hides the thing a reviewer needs to
see. `authorization-key.ts` does it in twenty readable lines and `privy.ts` shows
exactly where it goes on the wire. It is also one fewer dependency near the
payment path.

## Where the keys actually live

Each operator holds a P-256 authorization key. In this repo they are generated by
`scripts/privy-org-setup.ts` and pasted into `.env`, which is honest for a
hackathon and **wrong for production** — there, each key belongs on its
operator's own device or HSM, and the server holding the app secret should never
be able to read one.

This is the single largest gap between the demo and a real treasury, and it is
stated rather than left for a reviewer to notice. The design does not change:
Privy verifies signatures against registered public keys and does not care where
the private half slept.
